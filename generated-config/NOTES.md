## What the wallet query ID means

The wallet does not assign an OID4VP query ID to a stored credential. The verifier chooses a local DCQL query ID; transaction data's `credential_ids` must name that ID. This repository's prior wallet test used `credential_1`, so the authorization configuration and request template here use `credential_1`. The actual credential is matched by its VCT (`https://delegations.example/vct/delegation-auth`). EUDIPLO cannot inspect a wallet's private inventory in advance. The Paradym log from the earlier membership test showed a separate credential configuration ID `membership`; that is not this delegation credential and should not be referenced here.

## Dashboard setup

1. **Create or select a tenant.** In **Cryptographic Assets → Keys → Create Key**, create an `attestation` key chain for SD-JWT VC signing, an `access` key chain with an active certificate for verifier request signing, a `statusList` key chain (because both credentials enable revocation), and a `trustList` key chain (to sign your managed trust list). Select your own CA chain/certificate for the attestation key. The `keyChainId`/`accessKeyChainId` placeholders in the JSON must be replaced by the returned IDs. In **Cryptographic Assets → Trust Lists**, add your issuer as an internal entity. Its `issuerKeyChainId` is the attestation chain and its `revocationKeyChainId` is the `statusList` chain; the list itself is signed with the `trustList` chain. Select that trust-list ID in verifier configs.
2. **Issuer settings.** Under **Credential Issuance → Issuer Settings**, configure an enabled built-in authorization server, `batchSize: 1`, and `dPopRequired: true` if the wallet supports DPoP. Do not set `keyAttestationsRequired` unless you have configured and tested the relevant wallet-provider trust list and the wallet supplies a supported key attestation.
3. **Credential Types.** Under **Credential Issuance → Credential Types**, create/import `delegation_auth` and `agent_delegation` from the two credential files. Enable key binding, status management, the appropriate attestation signing key chain, and the displayed lifetime. For a custom VCT URL, publish the matching VCT metadata JSON yourself at that URL. More on this constraint below.
4. **PID enrollment verifier.** Create a verification config from `presentation/pid-enrollment.json`, after registering the EUDI PID issuer root(s) in a trust list accepted by EUDIPLO. The exact iOS reference-wallet PID VCT and trust-list material are not in this repository and must be taken from the wallet/issuer ecosystem release you are testing. The template deliberately has no claim allowlist because the PID claim names were not verified from this checkout; check carefully what the target wallet discloses for a query without `claims` before using it with real PID data.
5. **Delegation authorization verifier.** Create a verification config from `presentation/delegation-auth-authorization.json`. It asks for the auth credential by VCT with no `claims` array. Configure a managed trust list containing your own issuer chain. Each delegation starts a fresh request via the API example so the wallet sees the per-request transaction data. The request uses `credential_1` as the query ID.
6. **Agent verifier.** Create `presentation/agent-delegation-verification.json` for the token service, select the own-CA trust list, and request the claims the token service must inspect. This request has no transaction data.
7. **Results.** For the owner authorization request, use the inline webhook in the example if the backend needs the raw token. EUDIPLO sends one delivery attempt. Persist the verified outcome, transaction data, raw presentation, and consent hash on your backend. Poll `GET /api/session/{id}` (or subscribe to SSE) to reconcile status and failures.

### Raw presentation and consent hash

For a successful request, the inline webhook's `credentials[].rawToken` is the received SD-JWT VC token, including disclosures and KB-JWT. Store the exact signed presentation bytes and compute `consent_hash` over the exact stored bytes using the algorithm your backend documents (the API example labels it SHA-256). The `credential_1` identifier is only the request's DCQL alias. The session result provides verified/decoded claims and outcome; it does not provide raw token polling output. Failed presentations do not include raw tokens in the webhook.

### Signed metadata, DPoP and key attestations

- **Signed issuer metadata:** supported via an `Accept: application/jwt` request and signed with the tenant's access certificate. Keep a valid access key chain and certificate. Credential signing is separately done by the attestation key chain.
- **DPoP:** `dPopRequired` defaults to `true` for built-in authorization and credential endpoints. Leave enabled if the iOS wallet completes the flow; turn off only for an explicit interoperability test.
- **Key attestations:** not required by default. If enabled with `config.keyAttestationsRequired`, EUDIPLO requires a trusted wallet key attestation and accepted storage/user-authentication levels; the app ecosystem's trust-list support must be configured. A key attestation can carry up to `batchSize` keys; keep batch size 1 for this design.
- **Stable keys:** `keyBinding: true` writes the proven holder JWK to `cnf`; it does not control the wallet's key lifecycle or require the same JWK on future issuance.

## Config and environment values

| Purpose | EUDIPLO setting |
|---|---|
| Public issuer/verifier origin | `PUBLIC_URL=https://YOUR_STABLE_PUBLIC_HOST` (must be reachable from phone; certificate and `iss` must align). |
| Database encryption at rest | `ENCRYPTION_KEY_SOURCE=vault` plus `VAULT_ADDR` and `VAULT_TOKEN`, and a pre-created Vault KV v2 secret as described in EUDIPLO's encryption-key docs; or default `ENCRYPTION_KEY_SOURCE=env` with persistent `MASTER_SECRET`. |
| Signing key backend | `config/kms.json` (global) or tenant `kms.json`; choose a provider such as `vault` with `vaultUrl: "${VAULT_ADDR}"`, `vaultToken: "${VAULT_TOKEN}"`. This is separate from encryption-at-rest configuration. |
| Own CA and signing keys | Create/import a CA chain and an `attestation` signing chain through **Trust → Key Chains** or `POST /api/key-chain`; place the credential leaf certificate chain in the wallet-trusted path and set resulting key-chain ID on each credential. Create an `access` chain and set its ID on each verifier config. No private key or real certificate is included here. |
| Tenant | The tenant ID is used in issuer URLs and API authorization; set `TENANT` in the example shell and create the tenant in the dashboard/API. There is no EUDIPLO `TENANT` environment variable found. |
| Root dashboard login | `AUTH_CLIENT_ID`, `AUTH_CLIENT_SECRET`, and persistent `MASTER_SECRET` are deployment auth settings; they are not the per-application client credentials. |
| API client | Create a tenant client in **Settings → API Clients** (UI wording may vary by release) with least-privilege roles: `issuance:offer`, `presentation:request`, and session-read access as needed. Store client ID/secret in your backend secret store; no concrete client secret is included. |
| Issuer operational settings | `batchSize: 1`, `dPopRequired: true`, enabled built-in authorization server, and optional `walletAttestationRequired` only if tested/configured. These are tenant issuer config fields, not environment variables. |
